# tang role

Tang NBDE server for the clevis LUKS auto-unlock, run as a rootful Podman Quadlet unit (`tang.service`) directly on the host, NOT in k3s: the server has to be up while the cluster nodes are still sitting in their initrd waiting for it.

## Usage

```bash
ansible-playbook common.yml --tags podman,tang --limit k3smaster
ansible-playbook common.yml --tags iptables --limit k3smaster
```

Conditional on `providestang: true` (needs `wantspodman: true` for podman >= 4.4 with Quadlet). Runs before the `clevis` play in `common.yml`, so a host binding against a freshly deployed tang finds it serving.

## What it does

- Deploys `/etc/containers/systemd/tang.container` (image `tang_image`, `Network=host`, tangd directly on `tang_port`, default `9090`, no HAProxy/nginx frontend).
- `tang_data_dir` (default `/var/lib/tang`, owner `100:101` = `_tang` in the image) holds the JWK keys. They are **generated by tangd on first start and never deployed by Ansible**, so they live only on that host. Losing the dir means re-binding every clevis client against the new keys (`/root/setup_clevis_tang.sh`).
- Verifies `GET /adv` returns 200.
- `common` opens `tang_port` in `iptables.sh` for `localnets` on hosts with `providestang`.

## Backup

`tang-backup.timer` (tag `tang_backup`, gate `tang_backup_enabled`, default `true`, opt-in removal `tang_backup_teardown`, default `false`, schedule `tang_backup_schedule`, default daily 02:45 plus `tang_backup_random_delay`, `Persistent=true`) runs `/usr/local/sbin/tang-backup.sh`, which uploads every `tang_data_dir/*.jwk` to `<rustfs_rc_alias>/<rustfs_rc_backup_bucket>/tang/<inventory_hostname>/` with the host's `rc` binary and `/root/.config/rc` (installed by `k3sserver`, tag `rustfs_client`; the role only asserts they exist).

- The JWK filename is the key thumbprint, so objects are content-addressed: existing remote objects are skipped, nothing is overwritten or deleted, and rotated-away keys stay in the backup. Key contents are never printed.
- The script fails if `rc`, its config, or the data dir is missing, or no `*.jwk` exists.
- `tang_backup_enabled: false` only skips the install and deletes nothing. Removal: `ansible-playbook common.yml --tags tang_backup --limit k3smaster -e tang_backup_teardown=true` stops and disables the timer and removes the script and unit files. Remote objects are kept.
- The target is whatever `rustfs_rc_alias` points to (vault); off-box only if that alias is not the local RustFS. Anyone holding the JWKs plus a client's LUKS header can unlock that client, so treat the bucket like the vault.
- Restore: copy the `*.jwk` files back into `tang_data_dir`, `chown 100:101`, `systemctl restart tang`.

```bash
ansible-playbook common.yml --tags tang_backup --limit k3smaster
```

## Caveats

- A host cannot unlock itself via its own tang (the keys sit on its encrypted disk). `clevis_tang_servers` is therefore derived per client as every other `providestang` host (`t=1`); the only tang host gets an empty list and boots via the keyfile fallback (`clevis_keyfile_enabled`).
- The image tag is rolling (`latest`) and there is no auto-update timer; `podman pull` + `systemctl restart tang` to update.
